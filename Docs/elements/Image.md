[aspectRatio(_:contentMode:)](https://developer.apple.com/documentation/swiftui/view/aspectratio(_:contentmode:)-771ow),

Images come from Xcode asset catalogs read at build time (decision 0011): `scripts/assets.py`
turns every `*.xcassets` into a manifest plus the image files, the runtime selects a variant and
the painter loads it. Fixtures draw from `Fixtures/Assets.xcassets` (generated by
`scripts/gen-fixture-assets.py`).

## API surface

| API | Notes |

## Catalog rules (from Apple's format reference; consistent on both sides, not verified against actool)

- Name = folder namespaces (`provides-namespace: true`) joined with `/` plus the set name; a
  folder without the property is transparent. `Image("nested")` does not find `Folder/nested`.
- Variant selection: idiom `mac` before `universal` (others ignored); appearance matching the
  environment's `colorScheme` (`light`/`dark`) before `any`; the display scale's variant, else
  the largest scale (drawn scaled). Point size = pixel size ÷ scale.
- `template-rendering-intent: template` makes the image a template; `original` and absent do not.
- Missing name: 0 × 0, nothing drawn, no spacing lost (a `Text` after it still sits 8 pt away).

## Measured layout rules (macOS 26.2, `image/*` fixtures, 2026-09-02)

| Rule | Fixture / probe |
|---|---|
| A named image is rigid at its point size whatever the proposal: 64 × 40 from a 128 × 80 @2x file, 20 × 64 from a 2×-only set, 80 × 60 from a JPEG | `image/intrinsic` |
| A rigid image in a smaller `frame` keeps its size, centred, overflowing; `clipped()` cuts it | `image/resizable` `overflow`, `overflowClipped` |
| `resizable()` takes the proposal in both dimensions (30 × 30, 96 × 30, 300 wide for `frame(height:)`); two resizable images in an `HStack` share the width equally (150 each); unspecified dimensions fall back to the point size | `image/resizable` |
| Stack spacing is the plain-view 8 pt on every side, image to image, image to text and image to a `Color` box; vertically a `Text` keeps its font-derived distances (4.74 above, 8.15 below the 13 pt default font) | `image/stack-spacing` |
| Both text baselines of an image are its bottom edge | `image/stack-spacing` `baseline`, `lastBaseline` |
| `aspectRatio(nil, .fit)` on a resizable image proposed *w* × *h*: the largest rect of the image's ratio inside (64 × 40 in 100 × 40; 40 × 25 in 40 × 100), centred by the enclosing frame; `.fill`: the smallest covering rect (96 × 60 in 40 × 60), overflowing unless clipped | `image/aspect-ratio` |
| Explicit ratios: `aspectRatio(1, .fit)` in 60 × 40 → 40 × 40; `aspectRatio(CGSize(1, 3), .fill)` in 30 × 30 → 30 × 90 | `square`, `third` |
| One proposed dimension: `frame(width: 100)` → 100 × 62.5, `frame(height: 30)` → 48 × 30 | `widthOnly`, `heightOnly` |
| No frame: the stack's proposal is fitted (a 20 × 64 image in the 100 pt-tall row → 31.25 × 100) | `flexibleImage` |
| `aspectRatio` on a rigid image changes nothing (64 × 40 in 100 × 40); on `Color` it sizes the colour (100 × 50 in 100 × 100) | `rigid`, `colorRatio` |
| Model: ratio = explicit or the child's ideal size (`sizeThatFits(.unspecified)`); the child is proposed the fitted/filled rect and the modifier takes the child's answer | `_AspectRatioLayout` |

## Measured painting rules

| Rule | Fixture / probe |
|---|---|
| Template images are filled with the foreground colour where the source has alpha: primary (black at 85 %) by default, `foregroundColor(.red)` → 255, 56, 60, `foregroundStyle(.blue)` → 0, 136, 255 | `image/template` |
| `renderingMode(.template)` on a plain image tints it (a 64 × 40 green rectangle under `.green`, primary otherwise); `renderingMode(.original)` on a template set draws its pixels | `forced`, `forcedDefault`, `original` |
| `opacity` multiplies the drawn alpha (0.5 → 128) | `faded` |
| `resizable(capInsets:)` stretches the nine parts (corners rigid, edges stretched one way, centre both); `.tile` tiles from the top-left, the last column and row cut at the frame | `image/tiling` `sliced`, `tiled` |
| Cap insets with `.tile` tile the edges and the centre; the golden shows the bottom edge and corners missing (an AppKit drawing quirk, not reproduced: SwiftUIWeb draws all nine parts, within Tier B tolerance) | `slicedTiled` |
| A 2× file drawn at 1.5× (96 × 60 from 64 × 40) is resampled; `interpolation(.none)` picks nearest neighbour | `nearest` |

## Symbols (`Image(systemName:)`, macOS 26.2, `symbol/*` fixtures, 2026-09-04)

SF Symbols are never shipped (`Docs/ROADMAP.md`). A symbol image has two parts:

- **Layout** is measured. `scripts/symbol-metrics-table.py` reads the `symbol/catalog-*`
  goldens (240 common symbols in baseline-aligned rows) into `SystemSymbolMetricsTable`: the
  width, height and descent below the baseline of every symbol at the macOS text-style sizes
  10, 11, 12, 13, 15, 17, 22 and 26 pt, at 13 pt semibold and bold, and at 13 pt with the small
  and large image scales. `SystemSymbolMetrics.size` returns the measured triple at those
  variants; other point sizes scale the nearest measured size at or below linearly, other
  weights and scales apply the 13 pt ratios (light weights the inverse of semibold), all to the
  half point. Symbol frames are glyph bounds, so a 40 pt star (Apple 51.5 × 47) can come out a
  point or two off (`symbol/basic` `approximateRow`, allowed 2 pt in Tier A and Tier B).
- **Painting** is a stand-in. `scripts/symbol-glyphs.py` maps SF Symbol names to icons of the
  Lucide set (ISC licence, notice in the generated `SystemSymbolGlyphs.swift`) and converts
  their SVG (paths with arcs, circles, rects, lines, polygons) into cubic path commands on the
  24 × 24 grid; 1551 names over 609 icons, stored as string blobs parsed on first use (array
  literals of that size compiled into 80 MB of wasm). The outline is scaled uniformly to fit the
  frame and stroked with round caps and joins in the foreground colour, 2 grid units × 0.8 for
  regular weights (1.0 semibold, 1.2 bold and up, 0.6 light); `.fill` names fill and stroke,
  `.circle.fill`-style names fill their first element and stroke the rest in white. A symbol
  with a glyph but no measurement takes the star's size; a name without a glyph is 0 × 0 and
  draws nothing, as Apple does for an unknown name.

| Rule | Probe |
|---|---|
| 13 pt: star 16.5 × 16, chevron.right 10 × 13.5, ellipsis 14 × 4.5, rectangle.portrait 14 × 16, line.3.horizontal 16 × 8.5 | `symbol/catalog-13`, `body`, `chevron`, `wide`, `tall` |
| Text styles: caption (10) 13 × 11.5, title (22) 28.5 × 26, largeTitle (26) 33.5 × 31.5 | `caption`, `title`, `largeTitle` |
| `imageScale`: small 13.5 × 13, large 21.5 × 20.5 (≈ 0.81 and 1.28 of the point size); `bold()` 17 × 16.5, semibold 17 × 16 | `small`, `large`, `bold`, `semibold` |
| Baselines: the frame's bottom sits 3 below the baseline at 13 pt (2 at 10, 3.5 at 17, 4.5 at 22, 5.5 at 26), the ellipsis 2.5 above it; both text baselines are the same | `baselineRow`, `baselineRow2` |
| Labels centre a symbol half a cap height above its baseline with the cap height taken to the half point: 4.5 at 13 pt (a 16.08 tall label), 7.75 at 22 pt; catalog images centre on their own middle (`Docs/elements/Label.md`) | `labelIcon`, `labelTitleIcon`, `labelBodyIcon`, `labelImageIcon` |
| `resizable()` symbols take the frame (50 × 50; `scaledToFit` in 50 × 30) | `resizable`, `fit` |
| Unknown name: 0 × 0 | `unknown` |

### Variants (macOS 26.2, `symbol/variants`, 2026-09-05)

`symbolVariant` changes only which symbol is drawn: `star` + `.fill` takes `star.fill`'s frame
(16.5 × 16 at 13 pt, the same as `star`), `.circle` and `.circle.fill` take 15 × 15,
`bell.slash` and `bell.slash.fill` 15 × 16.5, `person.circle` at the title size 26 × 25,
`checkmark.square.fill` 15 × 14; a variant without a symbol of its own (`square` + `.rectangle`)
keeps the base. Rendering modes change no frame. The stand-in table lacks a measurement for
some variant names that have a glyph (`bell.slash.fill`, `checkmark.square.fill`): they resolve to
the next candidate with both, which is what SwiftUI's frames show.

## Verification (2026-09-02, symbols 2026-09-04, variants 2026-09-05)

`symbol/variants`: Tier A exact, Tier C 0.00 %, Tier B exact frames in Chromium, WebKit and
Firefox. `SymbolVariantTests` cover the candidate order, resolution to measured symbols,
accumulation and reset, unknown variants, and rendering modes with multi-style foregrounds.

Tier A: all 8 image fixtures exact (`image/swap` steps included); the 12 symbol catalogs and
`symbol/basic` exact except the scaled-size row (within 2 pt). Tier B for symbols checks frames
only (the glyphs are stand-ins): 13/13 fixtures with exact frames in Chromium, WebKit and Firefox. Tier B: frames exact in Chromium,
WebKit and Firefox; pixels 0 % for pixel-aligned draws, ≤ 0.5 % where an image is resampled
(`image/resizable`), 1.6 % for `image/tiling` (the AppKit bottom-row quirk above). Build:
`scripts/build-wasm.sh` runs `scripts/assets.py` on the package (the fixture catalog for the
Gallery) and `index.html` includes `assets/manifest.js` before the module script; SwiftPM itself
ignores an undeclared `.xcassets` and copies a declared one verbatim, so either is fine.

## Corners (sw-images, 2026-10-11)

- Vector sets: `scripts/assets.py` copies an SVG as it is (`vector: true`, its point size from
  `width`/`height` or the `viewBox`) and rasterises a PDF at 1×, 2× and 3× with `sips` as
  actool does (next to the PDF when only a manifest is written, so the manifest's files exist;
  skipped with a warning where `sips` is missing). The runtime lays both out at their point size
  (40 × 30 for the fixture's sets); the browser draws the SVG through `drawImage`, which scales a
  vector sharply at any frame, and the CoreGraphics painter rasterises it through AppKit at the
  draw's pixel size. The harness (decision 0011, no actool) rasterises a set's PDF or SVG at 2×
  the way actool would, so `image/corners` pins the point sizes and the drawings (Tier C 0.17 %,
  Tier B 0.22 %).
- Slicing: a set's `resizing` becomes `capInsets` (9-part, or the one axis of a 3-part mode) and
  `tilesCenter` on the resource; a `resizable()` image draws nine-part with them unless the view
  passes its own `capInsets` (`ImageTests`). SwiftUI's handling of a compiled sliced set cannot
  be measured without actool (and `Image(nsImage:)` ignores `NSImage.capInsets`, measured), so
  the rule follows Apple's documentation; the geometry itself is the measured `image/tiling` one.
- Dark variants: `dark/images` (a dark window): `dual` draws its dark file, a set without one its
  only file, a template the dark primary, and a redacted catalog image the dark placeholder ink
  (Tier C 0.00 %).
- `colorMultiply`, `luminanceToAlpha` and `saturation` on a catalog image filter its pixels like
  any view's (the colour-matrix groups; `image/corners` `multiplied`, `luminance`, `desaturated`
  through SwiftUI's rasteriser).
- A redacted catalog image is its frame in the placeholder ink: black at 13.7 % (`image/corners`
  `placeholder`, the same ink as text's; measured).
- Display P3 components stay used as sRGB (`display-gamut` is recorded, nothing reads it).

## Not yet covered

SF Symbol glyphs themselves (stand-ins only), symbols beyond the 240 measured (sizes fall back to
the star's), true multicolour and hierarchical layers (the stand-ins have one), `Image` from
`CGImage`/`NSImage`, `Color("name")` for a missing name (assumed clear), Display P3 as a wider
gamut, a PDF set's vector data at scales beyond 3× (rasterised), symbol sets and sprite atlases
in a catalog.
