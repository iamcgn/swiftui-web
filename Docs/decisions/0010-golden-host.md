# 0010. Goldens come from a hosted window, not ImageRenderer

Date: 2026-09-02
Status: accepted

## Context

Phase 1 goldens were generated by `GoldenGen` with frames from an `NSHostingView` in an
offscreen `NSWindow` and pixels from `ImageRenderer`. Both used the same `FrameCollector`, and the
renderer's preference callback ran last, so every committed `frames.json` actually held
**ImageRenderer's** layout. Adding behaviour steps to the generator separated the two collectors
and exposed a difference.

## Evidence (macOS 26.2, SwiftUI 7.2.5)

Measured with `Text("Hello")` probes in both hosts (`Harness` experiment, 2026-09-02):

| Font | Hosted window | ImageRenderer |
|---|---|---|
| none set (default) | **16 pt line, baseline 13** (= `.system(size: 13)`) | 18.5 pt line, baseline 14 (= `.body`) |
| `.font(.body)` | 18.5 / 14 | 18.5 / 14 |
| `.font(.system(size: 13))` | 16 / 13 | 16 / 13 |
| `.font(.title)`, `.largeTitle`, wrapped paragraphs | identical | identical |
| `Button("OK")` bordered | 42.5 × 24 | 42.5 × 24 |

So the only discrepancy is the **default font**: in a window it is the 13 pt system font, in
`ImageRenderer` it is the `.body` text style. Explicit fonts and everything else agree, which is
why the recorded text metrics (measured with explicit fonts in a window) matched the
ImageRenderer frames.

The bold trait also depends on the font kind. `.bold()` measured in a window:

| Font | `bold()` resolves to |
|---|---|
| point size (10–26 pt), default font | bold (w700) |
| `.largeTitle`, `.title`, `.title2` | bold (w700) |
| `.title3`, `.subheadline`, `.body`, `.callout`, `.footnote`, `.caption2` | semibold (w600) |
| `.headline` (already bold) | heavy (w800) |
| `.caption` | medium (w500) |

Window rasterisation (`NSView.cacheDisplay(in:to:)` into a 2× `NSBitmapImageRep`) produces a
transparent-background PNG whose bordered-button fill is black at 20/255 (ImageRenderer: 19/255).
A CLI process cannot activate, so its window is never key and controls draw their inactive look
(prominent buttons grey); `NSApp.activate` and a `canBecomeKey` subclass did not help. Setting
`.environment(\.controlActiveState, .key)` on the root restores the active look, which is what
SwiftUI itself reads. Borderless button labels are grey in a window (ImageRenderer drew a
placeholder).

## Decision

- The fidelity reference is what a key macOS app window shows: `GoldenGen` takes **both** frames
  and pixels from the hosted window with `controlActiveState == .key`; `ImageRenderer` is no
  longer used. All goldens were regenerated.
- `PlatformProfile.defaultFont` is `.system(size: 13)` on macOS; `Text` falls back to it when no
  font is set. `Font.bold()` / `Text.bold()` set a bold *trait* resolved per text style
  (`TextStyleMetrics.boldTraitWeight`), bold for point-size fonts.
- Fixture strings shown in the default font are recorded under `system:13:…` keys
  (`TextMetricsRequests.defaultFont`).

## Consequences

- Layout goldens with default-font text changed (16 pt lines instead of 18.5); Tier A stays exact
  on all 51 fixtures. `Docs/elements/Text.md` and `Button.md` record the corrected values.
- `Button` labels and plain text now share the default font, matching the window.
- Behaviour fixtures keep one hosted instance across steps, so view state evolves exactly as on
  screen (`foreach/identity`).
- Pixel goldens now show real window drawing (buttons, materials); Tier B tolerances are
  re-checked per element.
